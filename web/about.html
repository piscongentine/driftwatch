About DriftWatch

A small, open-source loop from feature store to drift alert

DashboardAbout

What it is

DriftWatch is a working example of machine-learning monitoring that runs on a laptop. Feast keeps the sensor features of a fleet of machines. A small model learns from that history. New batches of readings arrive, and some of them slowly drift. Evidently compares every batch with the training data, and this dashboard and the alerts show what changed.

A feature store is a shared place for the numbers a model uses, so training and serving read the same values. Drift means the data a model sees today no longer looks like the data it learned from, so its answers quietly get worse.

What it can do

Keep features in Feast

A file offline store for history and a SQLite online store for the latest values. Training data is built with a point-in-time correct join.

Train and score a model

A logistic regression on the older 60% of history, its decision threshold picked on the next 15%, and its accuracy, precision, recall and AUC measured on the newest 25%.

Watch live batches

Each batch is read back from Feast and tested against the training reference. Empty and tiny batches are handled, not hidden.

Raise alerts

When the drifted share passes a limit, a column keeps drifting, a feature view goes stale, or a batch could not be tested.

Check itself

We plant the drift, so the detector's own precision and recall are measured and tested in CI.

Feed a PR sprint

The Issue Lab holds one tiny reproduction per real upstream bug, and a four-week plan turns them into reviews and pull requests.

Why it is needed

Models fail quietly when their inputs move. Most students meet drift only in slides. Feast and Evidently are usually taught apart, but the hard questions live where they meet: what is the reference, where do live batches come from, what happens with an empty batch or a constant column.

New contributors also need a safe way into open source. DriftWatch turns real, current upstream issues into small reproductions with clear expected results.

How it compares

DriftWatch does not replace production tools. Feast now ships its own feature monitoring, Evidently has a monitoring UI and a hosted product, and managed platforms do much more. It is a better fit in these ways:

Where it fits better

  • Small enough to read in twenty minutes: one job per file, about 150 lines at most
  • No cloud account, no paid keys, no web framework, no npm build
  • Shows the join itself: Feast as the source of truth, Evidently as the checker, with the edge cases left in
  • A built-in path to contribute: the Issue Lab and the sprint

Where to use something else

  • Real production monitoring, scheduling, auth, and many users
  • Real data: ours is synthetic, and its model marks say nothing about real fleets
  • Anything at scale: it runs on one machine, on local files

What the reproduced bugs mean

The Issue Lab runs one small program for each of 20 real upstream bugs. Reproduced means we still see the bug in the installed version. For each one, in short: why it happens, what it means, the trouble it can cause, and how it can be fixed. The README has the full table, with the pull requests.

Evidently

  • #1929 nan on a constant column

    Why: one category leaves nothing to compare. Means: the score is not a number. Trouble: nan breaks totals and JSON. Fix: return p = 1.0.

  • #1914 G-test fails when sample sizes differ

    Why: expected counts are not rescaled. Means: it only works on equal-size samples. Trouble: the whole report aborts. Fix: rescale the counts, or use chi-square.

  • #1900 Divergence tests on empty data

    Why: nothing checks for an empty series. Means: a crash or a silent nan. Trouble: monitoring stops, or goes on with a bad number, when data goes missing. Fix: raise a clear ValueError.

  • #1907 alias= is dropped

    Why: seven helpers do not pass it on. Means: the name you give a test is ignored. Trouble: reports and alerts show the wrong label. Fix: pass alias through.

  • #1927 No sequential drift metric

    Why: a missing feature; batches are tested one by one. Means: slow drift stays hidden. Trouble: it is noticed late. Fix: add a CUSUM metric (ask the maintainers first).

  • #1902 No calibration metric

    Why: a missing feature. Means: you cannot check that confidence matches accuracy. Trouble: an over-confident model goes unnoticed. Fix: add ECE and a reliability diagram.

  • #1905 Dead link in the docs

    Why: the linked folder is not on main. Means: a docs error, not a code bug. Trouble: newcomers land on a 404. Fix: correct the link.

  • #1898 Quickstart lacks openai

    Why: the install line leaves it out. Means: the guide fails as written. Trouble: a new user gets stuck. Fix: add openai to the docs.

  • #1910 litestar 3 import path

    Why: an import path that litestar 3 removed. Means: a future break; fine today. Trouble: evidently ui may fail on litestar 3. Fix: import from litestar.plugins.pydantic.

Feast

  • #6787 Rows silently dropped

    Why: rows with the same key and time collapse into one. Means: fewer rows than you asked for, and no error. Trouble: lost rows and labels in training data. Fix: give each row a unique id.

  • #6817 Empty entity frame (not seen on 0.66.0)

    Why: per the issue, a row-wise step fails on empty input. Means: a crash instead of an empty result. Trouble: a job with zero rows can crash. Fix: handle the empty case.

  • #6819 Empty online request

    Why: nothing checks for zero rows. Means: an error instead of an empty answer. Trouble: an HTTP 500 looks like an outage. Fix: return an empty result.

  • #6796 Empty Arrow table

    Why: it reads the first batch of a table that has none. Means: an internal helper crashes. Trouble: an empty push can stop a pipeline. Fix: return early.

  • #6805 Precomputed retrieval loses order

    Why: results are filled by position after sorting. Means: answers do not match questions. Trouble: silently wrong values. Fix: map results back to the request rows.

  • #6821 ttl not enforced online

    Why: online reads skip the age check. Means: old values look fresh. Trouble: predictions from stale data. Fix: enforce ttl online.

  • #6808 Hyphenated project name

    Why: init skips the SQLite naming rule. Means: init succeeds, then loading fails. Trouble: a broken first project. Fix: reject the name.

  • #6790 Join key dropped

    Why: a shared name is treated as request data only. Means: valid input is rejected. Trouble: a misleading error when serving. Fix: also count it as a join key.

  • #6845 UI cannot create a feature view

    Why: the handler builds the source from a name only. Means: creating a view fails. Trouble: an internal error in the UI. Fix: resolve the source from the registry.

  • #6842 Version not in the UI (merged, not released)

    Why: the fix is on master but not in 0.66.0. Means: wait for a release. Trouble: little; harder support. Fix: upgrade when it is released.

  • #6815 On-demand function loses globals

    Why: it is rebuilt from source text alone. Means: it works where defined, not where served. Trouble: NameError when serving. Fix: change the serialization; keep functions self-contained.
